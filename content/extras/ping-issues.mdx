---
title: "How to diagnose and fix ping issues"
description: "Run a traceroute or MTR to find where lag or packet loss starts, and what to send support."
---

Our servers are in Singapore. Players in the Philippines usually see low ping, so steady high ping, packet loss or random disconnects mean something along the route is struggling. These tests show where it starts: on your Wi-Fi, at your internet provider, somewhere in between, or at the server. Run one before opening a ticket and attach the result; it saves a lot of back and forth.

**First, open https://atbphosting.com/network/.** It checks the whole path live: your ISP (PLDT, Globe, Converge, Smart, DITO), our DDoS protection, the data centre and our servers, and shows each ISP's typical ping right now. If it shows your ISP as slow, the problem is inside your ISP's network; another connection (mobile data or a different ISP) or a VPN usually works around it until they fix the route. If everything there is normal and only you lag, run the tests below.

In every command below, use only your server's IP address, without the `:port` part.

## Quick check: traceroute

A traceroute lists every hop between you and the server and how long each one takes to answer.

- **Windows**: open Command Prompt and run `tracert 123.45.67.89`
- **macOS or Linux**: open Terminal and run `traceroute 123.45.67.89`

Replace the address with your server's IP. It takes a minute to finish.

## Better check: MTR

A traceroute is a single snapshot. MTR keeps pinging every hop, so it catches loss that comes and goes.

**Windows**

1. Download [WinMTR](https://sourceforge.net/projects/winmtr/), extract it and open `WinMTR.exe`.
2. Enter your server's IP in the **Host** field and press **Start**.
3. Let it run for at least 1 to 2 minutes (100 packets or more), then press **Stop**.
4. Press **Copy Text to clipboard** and paste it in your ticket as text. Screenshots often get cut off, and then we cannot read the whole route.

**Linux**: install `mtr` from your package manager and run `mtr 123.45.67.89`. **macOS**: install it with Homebrew (`brew install mtr`).

## On a phone

Phones have no built-in traceroute, so install a free traceroute or MTR app from Google Play (Android) or the App Store (iPhone). Enter your server's IP as the target (no port), run it on the same Wi-Fi or mobile data you play on, and take a screenshot of the full result.

## When only some players cannot join or lag

If the server works for some players but not others, the test has to come from the players who have the problem, not from the server owner. Each affected player runs one of the tests above against the server's IP and sends the result together with their public IPv4 address (from any "what is my IP" site). We need both, and results from more players make the problem easier to find. This usually turns out to be the route from their internet provider to Singapore; mobile data or a VPN works around it until the route is fixed, but we need their results to report or fix it.

## Reading the result

- **Loss on one hop and every hop after it** points to a problem at that hop.
- **Loss on one hop only, with the hops after it at 0%** is usually fine. Many routers simply do not answer test packets.
- **Loss on your first hop or two** is your own router or Wi-Fi. Try a cable, restart the router, or move closer.
- **A big jump in time that stays high on later hops** is a slow or busy link at that point.
- Run the test two or three times, ideally while the lag is happening. One run can mislead.

## Sending it to us

Open a ticket on our [Discord](https://discord.atbphosting.com) with:

- the full MTR or traceroute result as text (a full screenshot if you tested on a phone), not a summary
- the public IPv4 address of each player who has the problem
- the time the lag happened
- whether it happens all the time or only sometimes, and whether other players see it too

If only one player lags while everyone else is fine, the problem is almost always on that player's connection.

## Minecraft: Bedrock players rubber-band but Java players are fine

Bedrock players (on a Bedrock server or joining a Java server through Geyser) send their movement to the server every tick, and the server checks each step. When a player's connection stalls for a moment, those steps arrive late and all at once, and the server pulls the player back. Java players move on their own and only report where they ended up, so the same short stall barely shows for them. That is why the same server can feel smooth on Java and jumpy on Bedrock.

This usually comes from the lagging player's own connection, not the server. On our servers, most Bedrock players hold a steady ping while one or two on the same server, at the same moment, get stalls of a few hundred milliseconds to several seconds. If every Bedrock and Java player lags together, the server itself is busy: check its TPS (`/tps`, or [spark](/games/Minecraft/Optimization/plugins)) instead.

What helps the player who rubber-bands:

- Use a cable or 5 GHz Wi-Fi, move closer to the router, and stop downloads, streams or updates on the same connection while playing.
- Try mobile data instead of Wi-Fi (or the other way round) for a few minutes. If the lag goes away, the problem is that connection.
- Run an MTR from the same device and network while it happens (see above, apps for phones too) and send it with the time in a ticket.

What server owners can change so the server pulls players back less often:

- **Bedrock server (Vanilla Bedrock or Endstone)**: in `server.properties`, `player-position-acceptance-threshold` is how far (in blocks) a player may drift before the server corrects them. New servers start at `1.0`; older ones may still have `0.5`. Set it to `1.0` (up to `2.0` for players on very shaky connections), keep `server-authoritative-movement-strict=false`, then restart.
- **Java server with Geyser**: Geyser has no setting for this; the pull-back comes from the Java server. In `spigot.yml`, check `moved-wrongly-threshold` and `moved-too-quickly-multiplier`. Servers set up with Auto Optimization already use `10.0625` and `100`, which almost never pull anyone back, so leave those as they are. If yours still has the Spigot defaults (`0.0625` and `10`), raise them (for example `0.5` and `20`, or up to the Auto Optimization values), then restart. If you run an anticheat plugin, check its settings for Bedrock or Floodgate players too, since it can cause the same pull-backs.
- Keep Geyser and Floodgate on their newest builds.

Looser values give movement cheats a little more room, so raise them only as far as you need. They make pull-backs rarer but do not remove the delay itself, and a bigger plan does not fix rubber-banding that comes from a player's connection.

## Minecraft: Paper Anti-Xray

On Paper servers, Anti-Xray engine mode 2 can cause lag for players on unstable connections or on busy servers. Try engine mode 1, restart, and see if the lag goes away. The setting (`anti-xray`, `engine-mode`) is in `config/paper-world-defaults.yml`. See [Anti-Xray](/running_a_server/anti-xray).
